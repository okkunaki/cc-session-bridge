状態管理の設計議論

cc-session-bridge の state.json と状態遷移を決めるための資料。論点ごとに、選択肢と推奨を並べた。返信は「T1はA、T2はA」のように、論点の番号と選択肢の記号で足りる。

前提（決定済み）

  • D-001 MCP サーバー（stdio）と .cc-bridge/ の共有ファイルで橋渡しする。タブごとに別プロセスが立つので、状態の唯一の情報源はファイル。
  • D-007 競合対策として、アトミック書き込み（一時ファイル + rename）、状態遷移の検証、channel_id ごとのディレクトリ分離を MVP で入れる。排他ロックは Phase 2 以降。
  • D-011 MCP SDK は v2（@modelcontextprotocol/server）を使う。

T1 状態の種類と遷移 決定: A（D-013）

決める点

  • 仕様書の3状態に builder_working を足すか。
  • 報告を受け取ったあと、idle に戻すか。

仕様書の状態は idle、waiting_builder、waiting_architect の3つで、戻りの遷移は書かれていない。次の図は、4状態にした場合の遷移で、仕様書にない追加分を黄色で示している。

状態名は決定済み（D-012）。主語と動作を名前に入れる。仕様書の waiting_builder は awaiting_builder_pickup、waiting_architect は awaiting_architect_pickup に対応し、追加する実装中の状態は builder_working とする。awaiting ... pickup は「（指示や報告が）〜による受け取りを待っている」の意味。

  • 仕様書にない追加

A4状態にする推奨

上の図のとおり、builder_working を追加し、報告の受け取りで idle に戻す。

Builder が指示を受け取った事実が記録される。2つの Builder が待っていても、指示は1回だけ渡る。Esc で止められたとき、状態が builder_working のまま残るので、「途中で止まった」と判別できる（T3）。

仕様書より状態が1つ増える。

B仕様書どおり3状態

戻りの遷移だけ足す。指示の受け取りでは状態を変えない。

仕様書に忠実で、状態が少ない。

指示の二重受信を防げない。実装中かどうかが状態に出ず、Esc で止められたときの判別ができない。

C4状態を Phase 2 に回す

MVP は B で作り、あとから builder_working を足す。

最初の実装が小さい。

状態遷移の検証は後付けが難しい（D-007）。あとで遷移表を作り直すことになる。

推奨の理由

状態の種類は、遷移の検証、再開、履歴のすべての土台になる。後から増やすと、検証の条件と保存済みの state.json の形式の両方を直すことになる。最初から4状態にするコストは小さい。

T2 不正な順序で呼ばれたときの扱い 今決める

決める点

  • T1 の遷移表と違う状態でツールが呼ばれたとき、サーバーはどう応答するか。
  • 例: 報告を受け取る前に、次の dispatch_to_builder が呼ばれる。実装中に、もう一度 dispatch_to_builder が呼ばれる。
Aエラーを返す推奨

状態は変えず、status: "error"、理由のコード、現在の状態、次にやることを返す。

状態が壊れない。エージェントが応答を読んで、人間に確認できる。

エージェントがエラーの扱いを誤ると、往復が止まる。ロールの指示文に、エラー時の動きを書く必要がある。

B上書きして続行する

新しい指示で、前の状態を捨てる。

往復が止まらない。

実装中の指示が黙って消える。履歴と状態が食い違う。

C呼び出しを待たせる

dispatch_to_builder も、idle になるまで待機する。

呼び出し側がエラーを扱わなくてよい。

何が詰まっているか見えない。待機が長くなり、T7 の問題が増える。

A の応答の例:

{
  "status": "error",
  "code": "invalid_state",
  "current_state": "builder_working",
  "message": "Builder が実装中のため、新しい指示は送れません。",
  "hint": "await_builder_result で報告を待つか、人間に確認してください。"
}

推奨の理由

2つのセッションの片方は人間が見ていない時間が長い。静かに状態が変わるより、止まって理由を出すほうが安全で、原因も追える。

T3 実装中に Esc で止められたときの復帰 今決める

決める点

  • Builder が実装している最中（ツールを呼んでいない間）に、人間が Esc で止めたとき、状態をどう扱うか。
  • 止めたあと、作業を再開する方法と、作業をやめる方法。

このとき、状態は builder_working のまま残る。Architect は await_builder_result で待ち続ける。サーバーは、Builder が止まったことを知る手段がない。T1 の A なら、この状況を「builder_working のまま動いていない」として扱える。

A再開できるようにする推奨

状態は builder_working のまま残す。人間が Builder に「続けて」と伝え、Builder が await_architect_task を呼ぶと、同じ指示が再度返る（status: "resumed"）。中止の操作は Phase 2 で作る。

MVP の実装が小さい。Esc のあとに、作業を続ける通常の流れが成立する。

作業をやめたいときは、state.json を手で編集する必要がある。

BA に、中止の操作を加える

人間の指示で状態を idle に戻す手段を、MVP から用意する。履歴には中止を記録する。Architect 側の待機には status: "aborted" を返す。

人間が詰まったときに、ファイルを編集しなくてよい。

操作の置き場所を決める必要がある（5つ目のツール、または CLI）。ツールにすると、エージェントが勝手に中止できてしまう。

C一定時間で自動的に中止する

builder_working が一定時間更新されなければ、自動で中止扱いにする。

人間が何もしなくても復帰する。

長い実装が、正当な作業中に中止される。実装中は更新が出ないので、時間の基準を決められない。

Esc で止められる場所による違い

  • Builder が実装中: 本論点。状態は builder_working のまま残る。
  • Architect が待機中: 状態は影響を受けない。あとで Builder の報告が届き、Architect が await_builder_result を呼べば受け取れる。
  • Builder が待機中（idle のまま）: 待機が中断されるだけで、状態は変わらない。

計測待ちの部分

  • 待機中の Esc が、サーバーにキャンセルとして伝わるか（T7 の計測で確認する）。
  • 伝わるなら、待機中の状態を後始末できる。伝わらなくても、A の設計は成立する。

推奨の理由

MVP で最も重要なのは、Esc で止めたあとに「続ける」ができること。中止の操作は、必要になった実感を持ってから、置き場所を含めて設計したほうがよい。ツールとして用意すると、エージェントが自分で呼べてしまうので、慎重に決めたい。

T4 channel_id とディレクトリ構成 今決める

決める点

  • 複数の Architect と Builder のペアが混線しないよう、channel_id をどこで指定するか。
  • ディレクトリの構成を、チャンネルごとに分けるか。

ディレクトリは、チャンネルごとに分ける案を前提にする（D-007）。仕様書 2.2 C の構成から、1階層深くなる。

.cc-bridge/
└── default/
    ├── state.json
    ├── to_builder.md
    ├── to_architect.md
    └── history/
        ├── 001_plan.md
        └── 001_report.md

注意

  • 2つのタブは、同じ .mcp.json を読む。そのため、設定ファイルでチャンネルを固定すると、同じリポジトリの中ではペアを分けられない。
  • 同じリポジトリで2組を動かしたいときの指定方法が、論点になる。
Aサーバーの起動設定で固定する

.mcp.json の引数か環境変数で、チャンネルを決める。

エージェントが毎回指定しなくてよい。

同じリポジトリでは、ペアを1組しか動かせない。別のペアを動かすには、リポジトリ（worktree）を分ける。

Bツールの引数で指定する

各ツールが channel_id を受け取る。省略時は default。

同じリポジトリで、複数のペアを動かせる。

エージェントが、毎回正しい値を渡す必要がある。

CB に、環境変数の既定値を加える推奨

引数が最優先。省略時は環境変数、それもなければ default。/architect と /builder は、チャンネル名を引数に取り、ロールの指示文に埋め込む。

通常は何も指定せず動く。複数のペアが必要なときだけ、チャンネル名を渡す。

優先順位の規則が1つ増える。

推奨の理由

仕様書は「channel_id（デフォルト: default）による名前空間分離」を求めている。引数で指定できる B 系が仕様に合う。1組だけ使う大半のケースでは、何も指定せずに済む。

T5 turn_count と人間確認 今決める

決める点

  • 何を1ターンと数え、上限をいくつにするか。
  • 上限に達したとき、どうやって人間の確認を強制するか。
  • 仕様書の「連続自動往復」を、どう実装するか。

仕様書は「連続自動往復回数が上限に達したら、人間の確認を要求する」としている。ただ、サーバーは、2回の dispatch_to_builder の間に人間が議論に加わったかを知る手段がない。そのため、「連続」と「自動」は、そのままでは判定できない。

ターンの数え方（提案）

  • 1ターン = dispatch_to_builder が成功した1回。
  • 上限は state.json の max_turns。初期値は 10。
  • 人間が解除するまで、turn_count は増え続ける。

「連続」の扱い

  • 人間の関与は検知できないので、「解除してからの往復回数」と読み替える。
  • 人間が確認して続けるときに、turn_count を 0 に戻す。
Aロールの指示文だけで頼む

「10往復したら人間に確認する」とプロンプトに書く。サーバーは数えるだけ。

実装が最も小さい。

強制力がない。エージェントが指示を忘れれば、ループが止まらない。

Bサーバーが拒否し、人間が解除する推奨

上限に達すると、dispatch_to_builder が turn_limit_reached のエラーを返す。人間が turn_count をリセットするまで、次の指示は送れない。MVP では state.json を手で編集し、Phase 2 以降で CLI を用意する。

サーバーが強制するので、エージェントの指示忘れに左右されない。エージェントが自分で解除できない。

解除の手間がある。

CMCP の問い合わせ機能で、人間に直接聞く

サーバーが、人間への確認ダイアログ（MCP の elicitation）を出し、承認されたら続行する。

人間が、その場で承認できる。ファイルの編集が不要。

Claude Code（VSCode 拡張）がこの機能を使えるか、未確認。確認が先に必要。

推奨の理由

ガードレールの目的は、エージェントが暴走したときに止めること。エージェント自身が解除できない仕組みにしたい。C は理想だが、使えるかを確認してから Phase 2 で検討すれば足りる。上限の初期値 10 は仮で、使いながら調整する。

T6 最新ファイルと履歴の関係 今決める

決める点

  • to_builder.md と to_architect.md（最新）と、history/（往復ごとの記録）を、両方保存するか。
  • 指示書と報告書の中身の形式を、MVP でどこまで決めるか。
A両方を保存する推奨

送るたびに、to_*.md を最新の内容で上書きし、history/ に連番で追記する。連番はターン番号（001_plan.md、001_report.md）。

人間が「今の指示」をすぐ開ける。履歴は追記のみで、消えない。仕様書どおり。

同じ内容が2か所にある。

B履歴だけにする

to_*.md は作らず、state.json が最新の履歴ファイルを指す。

重複がない。

人間が最新を探す手間がある。仕様書から外れる。

MVP での中身の形式（提案）

  • dispatch_to_builder の引数（目的・背景・対象・制約・完了条件）を、固定の見出しで Markdown に整形して保存する。
  • report_to_architect も同様（ステータス・変更ファイル・検証ログ・未解決の論点）。
  • 圧縮率を上げる形式の最適化は、Phase 2 の課題。

書き込みの規則

  • すべてアトミック書き込み（D-007）。
  • 履歴は、存在するファイルを上書きしない。
  • 書き込みの順序は、履歴、最新、state.json の順。状態の更新を最後にする。

推奨の理由

履歴は、このプロダクトの価値（設計意図と実装結果のペアの蓄積）そのもの。最新のコピーは、人間が追うときの入口として安い。状態の更新を最後にするのは、途中で止まっても、状態が先に進まないようにするため。

T7 待機の間隔・上限・進捗通知 Esc のみ計測待ち

いま決められないこと

  • pending を返す間隔（秒数）。
  • 待機ループの合計上限と、上限後の動き。
  • 進捗通知で、待機を維持するか。
  • 待機中の Esc を、サーバーがキャンセルとして受け取れるか。

タイムアウトの計測（2026-11-22 実施）の結果は次のとおり。サーバー側のログ（probe.log）と照合して確認した。

項目結果
待機の長さ10、30、60、120、300、600 秒（進捗通知なし）がすべて成功した。失敗は一度もなかった。600 秒は計測用ツールの上限で、それより長い待機は未測定
progressTokenClaude Code が、全ての呼び出しに付けていた。進捗通知は 300 秒の呼び出しで、5 秒ごとにサーバーから送信できた
進捗通知の延長効果未検証。タイムアウトが起きる条件まで測っていないため
待機中の Esc未検証。1回試したが、Esc が押されず、60 秒を完走した。再試行する
権限確認ダイアログ実行役の報告では出なかった。画面で出たかは、開発者の確認が必要

この結果から、仕様書の「30〜60 秒で pending を返す」は、少なくとも 10 分までは不要と言える。10 分を超える待機は、ドキュメントの記述（アイドルタイムアウト 30 分）を参考に、設計で扱う。

いまの仮案は次のとおり。

項目仮案根拠・依存する計測
待機ループの合計上限30〜60 分で待機をやめ、人間に伝えて止まる。再開は /builderあなたの使い方では、議論で4時間、夜は約16時間空く。PC のスリープ、5分ごとの pending によるコンテキストの消費もあり、長時間の待機に依存しない設計にする
pending の間隔計測で成功が確認できた範囲（最大で 600 秒）の中から選ぶ計測: 何秒まで切れないか
進捗通知の利用延びるなら、待機中に定期的に送る。延びなければ使わない計測: 通知で待機が延びるか。Claude Code が progressToken を付けるか
待機中の Escサーバーがキャンセルを検知できれば、待機を後始末する。できなくても T3 の A は成立する計測: キャンセルがサーバーに伝わるか

上の再開の方針は、T1 の4状態と T3 の A に依存する。状態は state.json に残るので、待機をやめても、指示は失われない。

各項目の役割

  • revision: 書き込みのたびに +1 する。書き込む前に、読んだときの値と一致するか確認し、他のプロセスが先に更新していたら失敗させる（競合の検出）。
  • turn_count と max_turns: T5。turn_count が max_turns に達すると、dispatch_to_builder が拒否される。
  • current: 実行中のターンの情報。T3 の再開で、同じ指示を返すために使う。
