# 決定ログ（Decision Log）

相談役セッションと開発者で決めた事項を、理由付きで時系列に記録する。新しい決定は末尾に追記する。覆した場合は元の記録を消さず、状態を「置換」にして新しい記録から参照する。

状態の凡例: 確定 / 暫定（実装時に再確認する） / 置換

---

## D-001: MCP サーバーとして構築する
- 日付: 2026-11-22
- 状態: 確定
- 決定: 2つのセッションの橋渡しを、ローカルの MCP サーバー（stdio）と `.cc-bridge/` の共有ファイルで実現する。
- 理由:
  - 実行中のセッションに外部のデータを届ける入口は、エージェント自身が呼ぶツールが最も素直で、戻り値がそのままコンテキストに入る。
  - ツール呼び出しが VSCode のタブ上で見えるため、リアルタイムな可視性と人間の割り込みを保てる。
  - ツール名が固定されるので、一度の allowlist 設定で確認なしに動かせる。Bash ポーリングは、コマンドが毎回変わり許可しにくい。
  - 入力スキーマで指示書の形を強制でき、出力の `status` を固定できる。
  - `.mcp.json` と `npx` だけで他のリポジトリに導入できる。
- 検討した代替案: 共有ファイル + Bash ポーリング、Hooks、`claude -p` / Agent SDK、Subagents、キー入力の自動送信。いずれも権限、待機中のセッションを起こせない点、可視性、コンテキスト分離のどれかを満たせない。
- 補足: 必須の手段ではなく、CLI を Bash で呼ぶ構成も原理的には成立する。

## D-002: 実装言語は TypeScript（Node.js 20 以上、ESM）
- 日付: 2026-11-22
- 状態: 確定
- 決定: TypeScript、Node.js 20 以上、ESM。依存は `@modelcontextprotocol/sdk` と `zod` から始める。
- 理由:
  - `npx` 配布が前提で、npm パッケージが最も自然。Python は `uvx`、Go や Rust はバイナリ配布になり、利用者の前提環境が増える。
  - 公式 SDK が TypeScript 版で最も成熟している。
  - Claude Code の利用者には Node.js が入っている可能性が高い。
  - ファイル監視、アトミックな `rename`、非同期のロングポーリングが標準機能で足りる。
- 関連する取り決め: stdout は MCP の通信専用。ログは stderr に出し、`console.log` を使わない。テストは vitest（必要になってから）、排他ロックは `proper-lockfile`（Phase 2）。

## D-004: ブランチ運用は `develop` への直接コミット
- 日付: 2026-11-22

## D-007: 共有ファイルの競合対策の方針
- 日付: 2026-11-22
- 状態: 暫定（実装時に開発者と再確認する）
- 決定: Phase 1（MVP）で、アトミック書き込み（一時ファイル + `rename`）、状態遷移の検証、`channel_id` ごとのディレクトリ分離（`.cc-bridge/<channel_id>/`）を入れる。排他ロック、指示の claim、役割の登録は Phase 2 以降。
- 理由:
  - stdio 方式ではタブごとに別プロセスが立ち、接点が `.cc-bridge/` のファイルだけになる。同じ役割の重複起動、残留した旧プロセス、手動編集で、書き込みの競合や二重受信が起こりうる。
  - 状態遷移の検証は後付けが難しいため、最初から入れる。
  - ロック、claim、登録は、複数セッションの運用が現実になってから入れても間に合う。
- 検討した代替案: HTTP 方式の常駐サーバー1つに各タブが接続する構成。状態をメモリ上に集約できるが、起動と終了の管理が必要になり、`.mcp.json` だけで導入できる手軽さが落ちる。

## D-008: コミットの粒度と担当
- 日付: 2026-11-22
- 状態: 確定
- 決定:
  - コミットは作業内容ごと、または後から戻しやすい粒度に分ける。1コミットには1つの目的の変更だけを入れ、無関係な変更を混ぜない。
  - コミットは Builder と Architect のどちらが行ってもよい。開発者（人間）はコミットを行わない。
- 理由:
  - 問題が出たときに `git revert` で必要な変更だけを戻せる。
  - 原因の切り分け（`git bisect` など）と、履歴の読みやすさが上がる。
  - 開発者がコミットに関与しない運用なので、粒度の基準を事前に決めておく必要がある。
- 補足: コミットメッセージは D-004 のとおり Conventional Commits。

## D-009: origin への push は開発者の承認があるときだけ、2段階で確認する
- 日付: 2026-11-22
- 状態: 確定
- 決定:
  - origin への push は、開発者が承認したときだけ行う。自発的には push しない。
  - 開発者から push を依頼されたら、すぐには push しない。先に、コミット状況（push 対象の未送信コミット一覧）と未コミットファイルを確認して開発者に提示し、「本当に origin に push してよいか」を再度確認する。2回目の承認を得てから push する。
- 理由:
  - push は外部に公開する操作で、取り消しにくい。
  - 何が送られるかを開発者が実際に見てから承認することで、意図しないコミットや未整理の変更の公開を防ぐ。
  - Builder と Architect が自動でコミットを積む運用では、開発者が個々のコミットを見ていない可能性が高いため、push 直前の確認が最後の関門になる。
- 適用範囲: Builder と Architect の両方。指示文には、この規則を制約として含める。

## D-010: scaffold での TypeScript 設定と依存バージョン

## D-011: MCP SDK は v1（`@modelcontextprotocol/sdk`）か v2（`@modelcontextprotocol/server`）か
- 日付: 2026-11-22
- 状態: 確定（移行の検証結果により、v1 に戻す場合がある）
- 経緯: scaffold では指示どおり `@modelcontextprotocol/sdk` 1.32.2 を使った。npm で確認したところ、v1 は最新が 1.32.2 で保守系統であり、v2 は `@modelcontextprotocol/server` 2.4.0 として別パッケージで公開されている。
- 現状の実装: `registerTool` と `StdioServerTransport` を使う `src/index.ts`（22行）のみ。移行コストは今が最も小さい。
- 決定: v2（`@modelcontextprotocol/server`）への移行を試す。scaffold と同じ検証（`initialize`、`tools/list`、`tools/call` の `ping`）が通れば v2 を採用する。通らない、または v2 に重大な問題がある場合は v1 のまま続け、その理由をこのログに追記する。
- 理由:
  - v1 は保守系統で、長期の OSS としては保守されている系統の上に積むべき。
  - 実装が22行のうちに移行するのが最もコストが小さい。状態管理やツールを実装してからでは、書き直しの範囲が広がる。
  - v2 は 2.4.0 まで進んでおり、初期の不安定さは過ぎている可能性が高い。ただし API は未確認のため、実際に試して判断する。
- 検討した代替案: v1 のまま進み、移行は必要になってから行う。当面のコストは低いが、移行の負担が後ろに積み上がる。
- 結果（2026-11-22）: v2 に移行できた。コミットは 454a8f5。**v2 を採用する。D-002 の依存指定（`@modelcontextprotocol/sdk`）は、`@modelcontextprotocol/server` に置き換える。**

  - 要件は Node 20 以上、`zod` 4.2 以上（4.6.7 で足りる）、`"types": ["node"]`。
  - コードの書き換えは import 2 行のみ。`McpServer`、`registerTool`、`StdioServerTransport`、`server.connect()` の使い方は変わらない。
  - 検証（`initialize`、`tools/list`、`tools/call` の `ping`）はすべて通った。差分は、`tools/list` の `ping` から `"execution":{"taskSupport":"forbidden"}` がなくなった点のみ。
  - `package-lock.json` が約1200行減った。依存が軽くなった。
- 未検証の点:
  - v2 は新しい protocolVersion（2026-07-28 spec）に対応し、`serveStdio`（新旧プロトコル世代を扱うファクトリ方式）が新設されている。現状は v1 と同じ `server.connect()` 方式で動いており、`serveStdio` には移していない。新しい protocolVersion のクライアントが接続したときの挙動は未検証。
  - `StdioServerTransport` は stdin の EOF で自分で閉じる（型定義のコメントより）。v1 との差異かは未確認。
  - Claude Code（VSCode 拡張）からの実接続は、まだ確認していない。

## D-012: 状態名は「主語 + 動作」で付ける
- 日付: 2026-11-22
- 状態: 確定（名前のみ。4状態の構成は D-013 で確定）
- 決定: 状態名を次のとおりとする。

| 状態の意味 | 状態名 | 仕様書の名前 |
| :--- | :--- | :--- |
| タスクなし | `idle` | `idle` |
| 指示が届き、Builder が未受領 | `awaiting_builder_pickup` | `waiting_builder` |
| Builder が実装中 | `builder_working` | （なし。T1 で追加を提案） |
| 報告が届き、Architect が未受領 | `awaiting_architect_pickup` | `waiting_architect` |

- 理由:
  - 仕様書の `waiting_builder` と `waiting_architect` は、主語が「待つ側」か「待たれる側」かを名前から判別できない。実際にブロックして待っている人（待機中のツール呼び出し）と、名前が指す人もずれる。
  - 状態名は `state.json`、エラー応答、ログに出る。読んだだけで意味が分かることを優先し、主語と動作を名前に入れる。長さは機械が読む名前なので許容する。
- 検討した案: 仕様書のまま（主語の役割が曖昧）、荷物ベース（`task_sent`、`report_sent`。誰の番かが名前に出ない）、受信箱（`builder_inbox`、`architect_inbox`。直感性が人によって分かれる）。
- 補足: `awaiting` は「〜を待っている」（他動詞 await の現在分詞）、`pickup` は「受け取り」（名詞）。`awaiting_builder_pickup` は「Builder による受け取りを待っている」の意味になる。
- 注意: `docs/spec.md` の状態名とは異なる。`docs/spec.md` は更新していない。

## D-013: 状態は4つ、報告の受け取りで `idle` に戻る（T1: A）
- 日付: 2026-11-22
- 状態: 確定
- 決定: 仕様書の3状態に `builder_working` を追加した4状態とし、Architect が報告を受け取ったら `idle` に戻す。遷移は次のとおり。

| # | ツール | 呼ぶ側 | 事前の状態 | 事後の状態 | 保存するもの |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | `dispatch_to_builder` | Architect | `idle` | `awaiting_builder_pickup` | 指示書、`turn_count` を +1 |
| 2 | `await_architect_task` | Builder | `awaiting_builder_pickup` | `builder_working` | 指示を返す（受け取りの記録 = claim） |
| 3 | `report_to_architect` | Builder | `builder_working` | `awaiting_architect_pickup` | 報告書 |
| 4 | `await_builder_result` | Architect | `awaiting_architect_pickup` | `idle` | 報告を返す（受け取りの記録） |

- 理由:
  - Builder が指示を受け取った事実が、状態に記録される。2つの Builder が待っていても、指示は1回だけ渡る（二重受信の防止）。
  - Builder が実装中に Esc で止められたとき、状態が `builder_working` のまま残るので、「途中で止まった」と判別できる（T3 の前提）。
  - 報告を受け取って `idle` に戻らないと、次の `dispatch_to_builder` が呼べず、2往復目が始められない。
  - 状態遷移の検証は後付けが難しい（D-007）。最初から4状態にするコストは小さい。
- 検討した案:
  - B: 仕様書どおり3状態で、戻りの遷移だけ足す。二重受信を防げず、Esc で止めたときの判別ができない。
  - C: 4状態を Phase 2 に回し、MVP は B で作る。あとで遷移表と `state.json` の形式を作り直すことになる。
- 補足: 呼ぶ側と事前の状態が合わない呼び出しの扱いは T2、Esc で止められたときの復帰は T3 で決める。仕様書（`docs/spec.md`）は更新していない。

## D-014: 待機とキャンセルの計測結果
- 日付: 2026-11-22
- 状態: 確定（計測結果。これに基づく設計は `docs/state-design.html` の T7 で決める）
- 方法: 仮設ツール `sleep`（`src/experiments/sleep.ts`、コミット c4a6ec9）を、実際の Claude Code（VSCode 拡張）のセッションから呼び、サーバー側のログ（`.cc-bridge/probe.log`）と突き合わせた。
- 結果:
  - **待機の長さ**: 10、30、60、120、300、600 秒（進捗通知なし）がすべて成功した。失敗は一度もなかった。600 秒は `sleep` の上限で、それより長い待機は未測定。
  - **`progressToken`**: Claude Code は、全ての呼び出しに付けていた。300 秒の呼び出しで、サーバーから 5 秒ごとの進捗通知を送信できた。
  - **進捗通知の延長効果**: 未検証。タイムアウトが起きる条件まで測っていないため。
  - **待機中の Esc**: `sleep(120)` を約 11 秒で中断できた。クライアント側は「rejected / interrupted」で、タイムアウトエラーとは別の扱い。サーバー側には、キャンセルが `AbortError: remote-cancel` として届き、待機が止まった（`done` は記録されず、`cancelled` が記録された）。中断後の同じセッションで、`ping` は正常に動いた。
  - **権限確認ダイアログ**: 実行役の報告では出なかった。画面での確認は、開発者に依頼中。
- 含意:
  - 仕様書の「30〜60 秒で `pending` を返す」は、少なくとも 10 分までは不要。
  - `await_*` ツールは、キャンセル信号（`AbortSignal`）を監視すれば、中断時に待機を止められる。
  - 待機を止めても、`state.json` の状態は変わらない設計にできる。
- 測っていないこと: 600 秒を超える待機、進捗通知の延長効果、Builder が実装中（ツールを呼んでいない間）の Esc、権限確認ダイアログの画面での挙動。
- 参考: 実行役が公式ドキュメントの検索結果から報告した値（本文は未読）は、ツールタイムアウトの既定が約 28 時間、stdio のアイドルタイムアウトが 30 分。実測では 600 秒まで確認できた。

## D-015: 遷移表と合わない呼び出しは、エラーを返す（T2: A）
- 日付: 2026-11-22
- 状態: 確定（方針）。ツールと状態ごとの具体的な応答は、T3 の決定後に表にする。
- 決定: D-013 の遷移表の事前状態と合わない呼び出しには、状態を変えずにエラーを返す。応答には、理由のコード、現在の状態、次にやることを含める。

```json
{
  "status": "error",
  "code": "invalid_state",
  "current_state": "builder_working",
  "message": "Builder が実装中のため、新しい指示は送れません。",
  "hint": "await_builder_result で報告を待つか、人間に確認してください。"
}
```

- 理由:
  - 状態が壊れない。静かに状態が変わるより、止まって理由を出すほうが安全で、原因も追える。
  - 2つのセッションの片方は、人間が見ていない時間が長い。エージェントが応答を読んで、人間に確認できる。
- 検討した案:
  - B: 上書きして続行する。実装中の指示が黙って消え、履歴と状態が食い違う。
  - C: 呼び出しを待たせる。何が詰まっているか見えず、待機が長くなる。
- 帰結: ロールの指示文（`/architect` と `/builder`）に、エラーを受けたときの動き（自動でやり直さず、人間に確認して止まる）を書く。待つ側のツール（`await_*`）は、待てば条件が整う場合はエラーにせず待機し、整わない場合だけエラーにする。具体的な表は T3 のあとに決める。

## D-016: ツール名は「送る物 + 向き」で付ける
- 日付: 2026-11-22
- 状態: 置換（D-017 で、短い名前に変更した）
- 決定: 4つのツールの名前を、次のとおりに変える。

| 呼ぶ側 | 動作 | 新しい名前 | 仕様書の名前 |
| :--- | :--- | :--- | :--- |
| Architect | 指示書（Plan）を送る | `send_plan_to_builder` | `dispatch_to_builder` |
| Builder | 指示書を待って受け取る | `wait_for_plan_from_architect` | `await_architect_task` |
| Builder | 報告書（Report）を送る | `send_report_to_architect` | `report_to_architect` |
| Architect | 報告書を待って受け取る | `wait_for_report_from_builder` | `await_builder_result` |

- 理由:
  - 送る側と受ける側で、同じ物に同じ語を使う。旧名は、同じ物が `report` と `result` に分かれていた。
  - 宛先（`to`）と送り元（`from`）を名前に含め、視点を統一する。旧名は、宛先の視点（`_to_builder`）と送り元の視点（`await_architect_`）が混ざっていた。
  - `dispatch` のような専門的な語を避け、平易な `send` と `wait_for` にする。
  - 履歴ファイル（`001_plan.md`、`001_report.md`）や、仕様書の用語（Plan、Report）と揃える。
  - 向きを名前に入れることで、Architect が Builder 用のツールを呼ぶような取り違えに、気づきやすくなる。
- 検討した案:
  - A: `send_plan` / `wait_for_plan` / `send_report` / `wait_for_report`。短いが、宛先が名前に出ない。
  - B: 仕様書のまま。上の問題が残る。
- 受け入れる欠点: 名前が長い。ツール名はコンテキストに毎回出るので、コストになる（MCP 上では `mcp__cc-bridge__send_plan_to_builder` の形）。実際の影響が大きければ、短縮を見直す。
- 帰結:
  - D-013 の遷移表と D-015 の応答例のツール名は、この決定で置き換える。当時の記述は履歴として残す。
  - `docs/state-design.html` は、新しい名前に更新した。
  - `docs/spec.md` は更新していない（状態名の D-012 と同じく、更新するかは別途決める）。
  - 状態の変化と待機の動作（D-013、D-014、D-015）は、名前の変更では変わらない。

## D-017: ツール名は短い形に変更する（D-016 を置換）
- 日付: 2026-11-22
